BLOCKING — must be fixed before launch
  [T14/T15] Ticket signing secret ships in the client bundle
        assets/ticket.js:10 — TICKET_SECRET, and ticket.js:15 truncates
        the signature to 6 bytes (48 bits).
        EXPLOITED: minted a signed QR for order "FAKE-00001-01", an order
        that has never existed, using only values readable in the bundle.
        The door scanner returned kind="ok" — admitted, green light.
        Anyone who opens DevTools can print free tickets for any event.
        FIX: 1) Sign server-side with a full-length HMAC-SHA256 (or sign
                asymmetrically and let the scanner verify with a public key).
             2) Remove the secret from the client entirely.
             3) Scanner calls a verify endpoint instead of trusting the payload.
             4) Treat the current secret as burned — do not reuse the value.

  [T4/T9/T15/T46] Owner and organizer portals are gated client-side only
        assets/dash.js:766, 777, 826, 836 — access is a single sessionStorage
        flag; the password hash and salt sit readable in localStorage ("ev_owner").
        EXPLOITED: with no credentials, set sessionStorage ev_owner_session="1",
        called ownerGate(), and reached the full platform dashboard — including
        the buyer monitor showing names and email addresses.
        The stored hash is also readable for offline brute-force (fast unsalted-
        speed SHA-256, no rate limit, no lockout).
        FIX: 1) Move authentication server-side; issue an httpOnly, Secure,
                SameSite session cookie.
             2) Enforce the role check on the server for every privileged
                request, not on page render.
             3) Hash with argon2id/bcrypt; add rate limiting and lockout.
             4) Require MFA for owner and organizer tiers.

  [T32] Price and entitlement are decided entirely in the browser
        assets/consumer.js:622 (totals) and 745 (order record).
        EXPLOITED: changed a $59.00 ticket to $0.01 in memory, completed
        checkout, and was charged $1.30 total. The order recorded $1.30 and a
        valid QR ticket was still issued.
        FIX: 1) Recompute every total on the server from stored prices.
             2) Create the Stripe PaymentIntent server-side; never accept a
                client-supplied amount.
             3) Issue the ticket only after the webhook confirms payment,
                verified against the raw body with the signing secret.


CRITICAL WARNINGS — fix this week
  [T46] /checkin/ has no authentication of any kind.
        checkin/index.html and assets/checkin.js contain zero auth calls.
        Anyone with the URL can open the door scanner, assign it to any
        event via its door code, and read the door log — which displays
        guest names. This is a staff tool exposing attendee PII publicly.
        FIX: put it behind organizer login and scope it to that organizer's
        events; treat the door log as PII.

  [T2] .env is not covered by .gitignore.
        No .env exists today and none appears in git history, so nothing is
        currently exposed — but the moment the backend arrives, one careless
        commit leaks it. Add .env, .env.*, and node_modules now.

  [T44/T49] No backup, restore, or encryption story.
        All state lives in one browser's localStorage; clearing site data
        destroys every order and check-in. Acceptable for a demo, must be
        replaced by a real database with encrypted backups before launch.


WARNINGS — fix before the next release

  [T42] No audit logging. The Scope of Work already requires logging every

UNLISTED FINDINGS
  Refund and cancellation cannot be enforced across devices. A refunded or
  event-cancelled ticket is only refused by a scanner sharing the buyer's
  browser, because a signed payload cannot be revoked without server state.
  A refunded ticket will scan green at a real door. Closed by the same
  server-side work as T14.

  Demo seed data contains realistic-looking personal data (22 buyer records
  with names, emails, phone numbers in assets/data.js). It is fabricated,
  but on a public brand domain it reads as real customer data. Keep the
  noindex protections and consider labelling it in-product.

TOP THREE ACTIONS
  1. Move ticket signing server-side and stop shipping the secret. Ticket
     forgery is proven and is the finding with direct revenue impact.
  2. Move owner and organizer auth server-side with real sessions and MFA.
     The buyer monitor exposes attendee PII behind a bypassable flag.
  3. Recompute prices on the server and issue tickets only on a verified
     Stripe webhook.
